# 社区宠物到家服务平台｜业务需求基线 PRD V0.1

> 文档状态：**需求草案，尚未冻结**｜日期：2026-10-14  
> 项目阶段：需求澄清与原型验证。**本阶段不启动正式开发。**  
> 原型对标：借鉴 TA岛宠物的预约、派单、上门履约、服务过程留痕思路；不复制其品牌、页面素材和不可见的内部规则。

## 0. 如何阅读

- **已知**：由项目发起人明确说明的事实。
- **建议**：用于启动讨论，不等于已确认需求。
- **待确认**：必须通过问卷、访谈或试点验证作决定；不得直接写入开发验收条件。
- **P0 / P1 / P2**：建议优先级，仍待确认。

## 1. 项目事实与定位

### 1.1 已知业务基础

1. 已有一个宠物综合体，包含**宠物公园、洗护、诊所、酒店、训狗场**。
2. 计划与社区合作，为每个合作社区提供宠物上门到家配套服务。
3. 社区提供**免费场地**用于设立线下接待站；实际使用期限、面积、管理权、费用分担等待书面确认。
4. 计划**先在两个社区试点**。
5. 项目还希望提供社区成员再就业岗位，目前明确提及**接待人员**；其他工种是否来自社区尚未确定。
6. 上门服务的运营流程可以参考 TA岛宠物。

### 1.2 项目定位（建议）

**“宠物综合体作为专业后端 + 社区接待站作为信任和获客前端 + 数字平台负责预约履约”**的社区宠物服务网络。不能把它误定义为单纯的宠托师自由接单平台。

价值链：社区方提供合作入口/空间 → 社区居民咨询和预约 → 总部配置服务与审核派单 → 合格人员履约 → 结果可追踪 → 转介洗护、诊疗、寄养、训犬等综合体项目。

### 1.3 双目标

- **商业目标**：验证订单需求、复购、服务毛利及向综合体转介的效果。
- **社区目标**：创造可持续的接待就业机会，提高社区居民获得可信赖的宠物服务的便利性。

不以“全国扩张”“融资规模”为试点阶段首要目标。

## 3. 利益相关方与角色权限

| 角色 | 主要职责 | 不应默认拥有的权限 |
|---|---|---|
| 居民 / 宠物主人 | 注册、建立宠物档案、选择服务、预约支付、查看报告、售后 | 看其他居民资料 |
| 社区接待人员 | 服务介绍、协助预约、核对服务区域、查询本站订单、协助转介和投诉登记 | 查看其他社区订单；调整价格；查看住户完整私密信息 |
| 上门服务人员 | 查看派给自己的任务、确认服务、打卡、填写清单、记录异常 | 浏览未分配客户或其他服务人员收益 |
| 总部客服/调度 | 审核服务范围、管理订单、调度、售后与异常升级 | 仅因后台权限而不加审计地访问敏感内容 |
| 总部运营管理员 | 服务和区域配置、价格、站点、员工、统计、权限 | 无审计修改履约证据 |
| 诊所/洗护/酒店/训犬负责人（候选） | 接收经许可的转介信息、安排具体专业服务 | 获得与其服务无关的住户信息 |
| 社区合作方（候选） | 查看合作绩效的**汇总数据** | 默认查看居民姓名、电话、家庭地址和宠物病例 |

所有角色需采用最小必要权限。员工账户状态、离岗权限回收、重要操作日志属于正式开发验收的一部分。

## 4. 居民上门服务核心流程

```text
扫描社区二维码 / 搜索服务
    ↓
选择社区（或系统预填，并允许修改）
    ↓
浏览服务目录 → 阅读服务说明 / 定价规则 / 服务边界
    ↓
填写宠物档案（品种/体型/行为/健康注意/紧急联系人等）
    ↓
预约上门地址、日期、时段、次数及进入住宅方式
    ↓
确认费用、风险告知、取消与隐私条款
    ↓
提交订单 → 付款/待付款（按最终支付规则）
    ↓
总部或授权调度人员派单 → 服务人员接单
    ↓
到场确认 → 按服务清单执行 → 拍照/视频/异常上报
    ↓
离场确认 → 服务报告 → 用户评价/售后
    ↓
可选：转介综合体其他服务
```

### 4.1 订单状态建议

`草稿 → 待支付/待确认 → 待派单 → 待接单 → 已排班 → 服务中 → 已完成`，并行异常状态 `取消中/已取消/退款中/已退款/异常待处理`。何时扣款、付款后超时未分配人员怎么处理，必须定义。

### 4.2 宠物与家庭入户关键信息

- 宠物：种类、数量、体型、年龄、习性、应激/攻击风险、疫苗及特殊注意（对不同服务采用差异化必填项）。
- 住宅：服务地址、是否有门禁、电梯、联系人、宠物所在位置、用品位置、钥匙交接或授权方式。
- 安全：明确许可操作、禁止操作、宠物走失/伤害/财物损坏应急流程、紧急联系方式。
- **不建议**在开放备注字段长期保存明文门锁密码。临时授权、代管钥匙应另设制度、授权与留痕。
- 服务照片/视频仅在必要和被授权的情况下记录，应有住户隐私与保存期限规则。

### 4.3 居民端异常情况（开发前需回答）

1. 服务员无法进门 / 门锁失效 / 客户临时取消。
2. 宠物不在房间、走失、攻击、惊吓、呕吐、受伤或死亡。
3. 宠物需要紧急送医，客户无法联系。
4. 服务员迟到、缺勤、拍摄证据缺失。
5. 用户对服务质量提出异议、退款或理赔。
6. 同一时段订单超出服务承载能力。

**建议应急机制**：服务人员一键停止服务并报备 → 总部客服/值班负责人接管 → 按授权联系主人和诊所 → 留存处置记录 → 售后复盘。

## 5. 社区接待站流程

```text
居民到站咨询 / 被社区引导到站
   → 介绍服务及站点可服务范围
   → 协助建立账户/宠物档案（征得本人同意）
   → 代为选择服务、时间和填写订单
   → 居民本人确认价格与授权
   → 生成订单，后续可查询状态
   → 需要专业服务时转介宠物综合体
   → 受理反馈并移交总部
```

### 5.1 接待岗位建议职责

- 解释平台的服务与价格；推广社区二维码。
- 用接待工作台协助年长或不熟悉智能手机的住户完成预约。
- 与总部运营保持联系，预约异常或投诉只**登记和升级**，不擅自作医疗判断。
- 每日做交接记录和简要报表。
- 由谁雇佣、谁发工资、培训时长、站点排班由问卷明确。

### 5.2 站点运营待确认

站点面积、营业时间、网络和电力、宠物是否允许进入、是否会发生实物交接、场地使用协议年限、宣传渠道、值班人数、数据访问边界、工作安全与财产责任。

## 6. 对接综合体既有业务

不应为了初期上线立即重建已有诊所/洗护/酒店/训犬管理系统。建议第一阶段支持：

- 展示服务介绍和联系方式；
- 提交服务预约意向，记录来源社区；
- 总部人工确认预约时间；
- 记录转介状态（咨询→联系→到店/履约→完成）；
- 若现有系统可对接，再另行评估接口与建设成本。

专业医疗预约与在线诊断要分开。涉及诊疗、药品、操作资格和跨地点服务时，需由当地专业人员及法律顾问审核。

## 7. 两社区试点建议功能分期

### P0：需求确认后开发的最小可用版本（提议）

**居民端**：社区切换、服务目录、宠物档案、服务信息说明、预约表单、价格确认、订单查询、服务报告、联系站点。  
**接待站端**：辅助下单、本站订单与预约查询、基本咨询记录、转介登记、异常上报。  
**服务人员端**：仅查看已分配任务、接单/到达/完成、清单与照片、异常上报。  
**总部端**：社区/站点管理、服务与价格设置、人工派单、员工与权限管理、订单总览、基础经营指标。  
**公共能力**：登录/授权、角色权限、关键事件日志、消息通知、退款/取消规则、基本隐私保护。

### P1：试点数据成立后考虑

组合套餐、会员/次卡、多个站点人员排班、订单分润与结算、服务质量评分、单据导出、宠物酒店/洗护深度预约、推广码归因、区域定价、售后赔付管理。

### P2：规模化后评估

智能派单、骑手/宠托师路径优化、实时直播、精细化会员 CRM、复杂财务结算、社区拓展与加盟授权、多城市运营。

## 8. 关键数据对象（仅概念层）

1. 社区 `Community` 与线下站点 `Station`；
2. 客户 `Customer`、宠物 `Pet`、服务地址/进入授权 `ServiceLocation`；
3. 服务项目 `ServiceCatalog`、区域/时段定价 `PriceRule`；
4. 订单 `Order`、服务任务 `Job`、派单/排班 `Assignment`；
5. 服务人员 `Worker`、培训和认证记录 `Qualification`；
6. 到场/离场、服务清单与图片等 `ServiceEvidence`；
7. 异常/投诉 `Incident`、服务评价 `Review`；
8. 支付/退款 `Payment`、结算配置 `SettlementRule`；
9. 综合体转介 `Referral` 与转化追踪；
10. 权限角色 `Role` 与操作审计 `AuditLog`。

以上仅为数据域，不代表已决定数据库或技术架构。

## 9. 经济模型与试点指标

### 9.1 单笔经营测算（等待真实报价）

`客户实际付款 − 服务员劳务成本 − 支付手续费 − 交通/物料 − 售后与保险准备金 − 分润/营销成本 = 订单贡献毛利`。

社区提供免费场地**不代表接待站零成本**；工资、电网、培训、宣传、管理、设备及保险仍需核算。

### 9.2 试点 KPI（目标值暂留空）

| 指标 | 目的 | 目标值 |
|---|---|---|
| 每站有效咨询量/周 | 验证社区获客 | 待定 |
| 咨询→付费转化率 | 验证销售流程 | 待定 |
| 每周完成订单 | 验证基础需求 | 待定 |
| 30/60日复购率 | 评估可持续性 | 待定 |
| 准时服务率与异常率 | 验证履约质量 | 待定 |
| 单笔订单贡献毛利 | 判断盈利可行性 | 待定 |
| 综合体服务转介转化 | 评估协同价值 | 待定 |
| 社区接待岗位数、留岗率 | 验证再就业成效 | 待定 |

## 10. 试点主要风险与待确认保障

| 风险 | 业务规则/控制建议 |
|---|---|
| 住宅进入与钥匙保管 | 单独授权、交接登记、可追溯、限制访问 |
| 宠物疾病、伤害、走失 | 事前筛选、人员培训、应急预案、保险适配 |
| 人员入户财物纠纷 | 身份核验、清晰服务边界、时间证据和投诉机制 |
| 误以为提供无资质医疗服务 | 把“诊疗预约/转介”与“诊疗实施”明确分开 |
| 社区人员用工责任 | 先明确劳动关系、培训、工伤/商业保险承担方 |
| 住户数据泄露 | 分角色访问、授权采集、保留/删除规则、社区侧仅汇总 |
| 免费场地合作不稳定 | 写明场地可用期、变更、设备和责任归属 |
| 节假日订单爆发 | 容量上限、暂停接单和服务等级规则 |

本文件不构成针对某一城市的合规意见，落地前要按实际所在地审核当地宠物服务、诊疗、隐私、保险、用工和社区物业规则。

## 11. 原型范围与确认方法

对应《03_UI信息架构与验收》，先评审可点击低保真页面，**冻结的是页面与操作逻辑，而不是品牌视觉**。

第一轮走查必须完成四条路径：

1. 住户自行预约上门喂养 → 派单 → 服务报告；
2. 社区接待人员辅助居民下单 → 总部收到预约；
3. 服务人员到场/执行/异常上报 → 总部介入；
4. 用户从社区入口预约洗护/酒店/诊所/训犬 → 记录转介。

## 会影响其他三端的业务变更

### B01 服务范围从“所属社区限定”转为距离与运力判断

最新评审提出放开跨社区，并给出“按距离设限”或“额外收费”两个方向。旧答卷 S03 的“不提供跨社区服务”应保留来源，但在后续基线标记为“评审提出调整，具体规则待确认”。

需明确：从站点、宠物师当前位置还是其他基点计算距离；最大服务范围；加价的触发、算法及报价确认；哪个站点负责；可派人员、行程时间与容量。

影响用户地址和报价、站点归属和接待、总部派单、工作人员路程和报酬；客户资料仍应按授权岗位隔离，跨社区服务不等于所有站点可自由查看全部客户。

### B02 追加服务必须区分申请、接单与欠费结算

评审对“追加账单”的含义提出疑问，不能据此认定所有后续欠费已被否定。建议分开：

1. 已经由客户确认且有服务事实的费用：展示原单、项目、金额及待付原因。
2. 服务中或结束后的新服务申请：重新核对原人员是否仍可服务、是否下班、是否有后续冲突，并由人员/调度确认。
3. 原人员不可承接：提示调整时间或发起普通新预约，不承诺自动指定原宠物师。

需明确可追加窗口、哪些项目可追加、付款与人员确认的先后，以及拒绝或超时后的处理；不能自行设置分钟数、金额或默认强制接单。

### B03 售后由群沟通转为回访或一对一企微

评审明确反对把投诉和售后引导到群。原 B03 的服务协同群不应继续直接充当售后入口。用户端、站点跟进、总部工单及回访记录需一致调整。

回访电话是必填业务字段。原型使用演示电话；正式实现需要受控工单数据保存和岗位访问，不能沿用公开问卷 GitHub Issue 保存真实回访电话号码。

### B04 “待结单”已明确为服务后的客户确认阶段

2026-10-23，项目负责人在本会话明确选择：“指‘待结单’：服务结束后等待客户确认完成”。

2026-10-23 补充要求：订单状态全部写成完整中文。客户确认阶段使用“订单结束待客户确认”，客户确认后使用“客户已确认订单服务完成”；四端列表、筛选、详情和报告保持同一含义。

刚提交的预约不使用“待结单”。本轮澄清未要求取消预约审核或调整付款先后，原审核→付款→派单流程暂保留；审核内容与提示按 U04 改清楚。总部抽查不作为每单结单的前置条件。

### B05 影像授权的入口与修改阶段

评审提出下单时由客户授权，服务开始前可修改。当前原型下单已有入口，但过程页仍可随时修改，需统一阶段说明与限制。拍照和直播仍为独立授权，不把“服务前可改”推断为开始后不得请求停止记录。

### B06 活动发布完整性与预热状态

需区分草稿、预热、开放报名、报名结束、已完成/取消等展示。上述状态拆分是实现建议；明确要求为“预热不报名”和“未规划好不允许开放发布报名”。发布前缺少条件、收费内容和取消规则时，不得以“待确认”占位进入可报名状态。

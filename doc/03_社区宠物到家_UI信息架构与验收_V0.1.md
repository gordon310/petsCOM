# 社区宠物到家｜UI 信息架构与流程验收 V0.1

> 状态：讨论原型（不是正式视觉稿，也不是正式产品）  
> UI 宗旨：**让居民容易预约，让社区接待员容易协助，让服务人员按步骤安全履约，让总部能统一运营。**  
> 参考对象：TA岛宠物的“选服务—下单—派单—履约记录”流程；UI 信息架构必须适配“两个社区接待站+一个综合体”。

## 1. 原型优先级：先交互、再视觉

V0.1只验证内容和流程，不确定品牌颜色、插画、logo、市场报价或实际平台技术栈。页面内出现的样例社区、样例宠物和订单均为演示数据，禁止当作真实运营信息。

## 3. 导航方案（待最终设计）

- **居民端底部四栏**：「首页」「服务」「订单」「我的」；顶部显示社区选择和接待站入口。
- **接待工作台**：「今日」「代约」「本站订单」「转介」；站点名称保持可见且不可随意切换到无权限社区。
- **服务人员端**：「任务」「进行中」「消息」「我的」；未分配任务无法浏览。
- **后台桌面侧边栏**：「总览」「订单/派单」「社区/站点」「人员」「价格/服务」「异常/报表」。

## 4. 四条必须走通的评审故事

**故事 U01：自行预约。** A 社区猫主人通过专属二维码打开首页，默认选中 A 社区；选喂猫 → 宠物档案 → 时间与地址 → 费用/告知 → 确认 → 能看到订单状态。

**故事 U02：接待员协助。** A 社区一位不熟悉智能手机的居民到服务站；接待员从工作台创建/查询客户并代填预约；**居民本人**确认费用和入户授权；总部接到来源为 A 社区的预约。

**故事 U03：履约与异常。** 上门人员只看自己被指派订单，查看风险信息和授权范围；到场打卡、清单操作、提交服务照片；遇到宠物异常可一键升级总部值班人员，而不是自行医疗处理。

**故事 U04：综合体转介。** 居民在社区入口选择洗护/诊所/酒店/训犬，留下预约意向，总部将其分配给对应业务部门；系统能够统计这个客户来自哪个社区。

## 5. 界面中的可见规则

1. **社区归属是核心字段**：首页顶部、订单、接待工作台和后台均能识别所属社区。
2. **两种预约模式**：居民自己预约；接待人员辅助预约，二者需有不同授权/操作日志。
3. **服务目录分层**：上门到家类与综合体到店/接送类清晰分离，避免把预约转介误认为即时可下单。
4. **所有“价格/时长”暂用“待确认/示例”**，避免原型造成承诺。
5. **最少必填项**：服务、宠物、日期时段、区域、联系方式、入户授权；补充字段按服务类型调整。
6. **关键安全提醒**：第一次无人入户、特殊健康问题、危险犬/攻击史、重要财物保护、录像/拍照权限均应有明确提示或单独确认。
7. **异常不是售后备注**：独立可见的紧急上报通道。
8. **社区方数据与用户个人资料隔离**，站点管理员只看授权范围。

## 6. P0 原型验收标准

- [ ] 可以切换 A/B 社区，首页和订单保留正确站点来源。
- [ ] 服务目录区分上门订单和综合体预约/转介。
- [ ] 用户能完成最短预约路径，无须反复填写宠物信息。
- [ ] 接待端能够演示代理预约并标记居民确认环节。
- [ ] 上门端能演示接单、打卡、清单、服务报告、异常上报。
- [ ] 总部可看到两社区订单并手动指派人员。
- [ ] 无在线支付/定位/直播时，原型明确标记为“模拟/未接入”。
- [ ] 项目方确认每屏“必填/可选/不采集”的字段及敏感信息处理边界。
- [ ] 项目方确认所有按钮的业务结果、错误提示与取消分支。

## 7. UI 视觉和设备建议（待审核）

- 居民：简单、可信赖、适合社区老年用户，采用大按钮、清晰中文、短流程、显眼电话咨询。
- 接待：不依赖熟练电脑操作，注重搜索/帮助预约/当日待办；平板或台式机均可。
- 服务人员：户外单手可操作，步骤检查必须明显，避免服务遗漏。
- 总部：以多社区运营、任务状态、人员可用性、异常处置为重点，电脑端优先。
- 色彩、品牌名、Logo、图标、页面文案在确定目标群体和市场后统一设计。
